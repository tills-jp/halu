## 0. 種別決定の経緯

商品マスタ（商品ＩＤ・商品名称・標準単価・備考の4項目）を対象に、一覧テーブル上で直接編集・追加・削除まで完結させる画面のため、`screen_types.md` の `list-mainte`（`SingleTableListForm*.mixin` 使用）に該当する。別画面への遷移は行わない。同じ最小構成マスタである顧客マスタの `CustomerListMainte`（正典実装）と同一パターンとし、画面挙動・実装方式はCustomerListMainteを踏襲する。

画面タイプの選定（list-mainte）と項目構成（商品コード・商品名称・標準単価・備考）は**2026-08-04に依頼者確認済み**（承認記録簿A-018。要件定義書REQ-014へ商品コードを明記）。当初は本設計時のAI判断（AI補完マーク）だったが、同日のデータモデル是正で確定した。

## 1. 要件

| 要件ID | 区分 | 要件 | 背景・理由 |
|--------|------|------|-----------|
| REQ-001 | 表示 | 削除フラグ='0'の商品を全件、一覧テーブルに表示する（ページングなし） | 一覧＋行編集で完結させる方針のため全件表示とする（CustomerListMainteと同方式） |
| REQ-002 | 編集 | 一覧内で商品名称・標準単価・備考をテーブルセル上で直接編集できる | 別画面遷移せず一覧内で完結させるため（list-mainteパターン） |
| REQ-003 | 追加 | 「行追加」ボタンで末尾に空行を追加し、新規商品を登録できる | 商品ＩＤはSERIAL自動採番のため、新規行では入力不要 |
| REQ-004 | 削除 | 「選択」列のチェックボックスにチェックを付けた行のみを、「削除」ボタン押下で削除（削除フラグ='9'の論理削除）できる。チェック無しで押下した場合は警告する | 誤操作防止（CustomerListMainte C-012の既定を踏襲） |
| REQ-005 | 選択操作性 | 「全選択」ボタンで、既存行（商品ＩＤ入力済み）の削除チェックを一括ON/OFF（トグル）できる | 複数件削除時の操作性向上（CustomerListMainte C-011の既定を踏襲） |
| REQ-006 | 登録 | 「登録」ボタン押下時、削除チェックの無い行のみを対象に、商品ＩＤの有無でINSERT/UPDATEを自動判定する | 一覧上の新規追加行と既存行の混在編集に対応するため |
| REQ-007 | 一意性 | 商品コード（業務キー）は必須入力とし、重複した商品コードは登録できない | CSV取込・帳票・人間による識別に使う業務キーのため（要件定義書REQ-014・A-018）。DBのUNIQUE制約を最終防衛線とし、画面には分かりやすいメッセージを返す |

| 操作 | キー | 動作 | 遷移先 |

| 全選択 | - | 商品ＩＤが入力済みの行（＝既存行）の削除チェックを一括ON/OFF（トグル）する。新規追加行（商品ＩＤ空欄）は対象外 | - |

## 5. 特記事項

- **実装はCustomerListMainteを正典とする（C-026是正内容に追随）**: execKindによるクライアント側の行フィルタ（登録=チェック無し行のみ／削除=チェック有り行のみを送信）は、コントローラが`this.model.execKind`に`"register"`／`"delete"`をセットし、`on実行OfCheckRequestData`（`ProductListMainte.model.js`）が送信直前に削除チェック値で明細行を絞り込む方式とする。**実装上の注意（C-026）**: `SingleTableListFormModelMixin`の`on照会OfCheckRequestData`は`on実行OfCheckRequestData`へ委譲するため、この行フィルタは必ず`mode == "execute"`のガード付きで実装すること（ガード無しだとselect（照会）時にも絞り込みが走り、selectリクエストの空のdetailレコードに対して例外となり初期照会が沈黙する）。
- **UPDATE/INSERTの自動判定と商品ＩＤの採番（C-026是正内容）**: サーバー側`ProductListMainte_execute_sql.json`は`update`→`insert`→再照会（`detail`）の順で定義し、共通クラス`SingleTableListForm_model.setData`（`Sample/Server/Commons/SingleTableListFormModel.py`）が、送信された明細行のうち商品ＩＤが入っている行を`update`用SQLの入力に、商品ＩＤが空欄の行を`insert`用SQLの入力に振り分ける。**商品ＩＤの採番はDBのSERIALに委ねる**: `insert`用SQLの`input.record`には商品ＩＤを**含めない**（含めると論理削除済み行のＩＤと衝突して主キー重複になる）。また`insert`の`削除`（削除フラグ）は画面値ではなく**`funct: "'0'"`でリテラル固定**とする（新規行の画面値は空のため、画面値のまま登録すると`削除フラグ='0'`の照会条件から漏れて登録直後の行が一覧に表示されない）。削除は`update`と同じ`execute`トランザクション内で、クライアント側フィルタにより「削除チェック有り行のみ」を送信することで実現する（サーバー側は"通常の更新"として処理し、削除フラグを'9'として保存する論理削除。物理削除ではない）。
- **商品コードの重複チェック（REQ-007）**: DBの**部分一意索引**（`商品_商品コード_有効_UX`。削除フラグ='0'限定）を最終防衛線としつつ、**クライアント側で一覧内の重複を検出**して「商品コードが重複しています。（{コード}）」を表示し送信しない（`ProductListMainte.model.js` の`getDuplicateProductCode`をcontrollerの`on実行`から呼ぶ）。本画面は削除フラグ='0'の商品を全件表示するため、**既存行との重複も新規行同士の重複も画面内で検出できる**。**実装方式の判断**: 正典（UserDetailMainte）の`"check": "found error"`＋`errormsg`によるサーバー側事前チェックは、`SingleTableListForm_model.setData`がSQLチャンクid（`update`/`insert`/`delete`/`insert_natural`）でしか分岐しないためチェック用チャンクへ明細行を流し込めず、本パターンでは採用できない（2026-08-04にコード確認）。
- **論理削除済み商品コードの再登録**: 一意制約を有効行限定の部分索引にしたため**再登録できる**（2026-08-04実測: 論理削除したST009を再登録し、削除フラグ='9'の旧行と'0'の新行が併存）。これはユーザコードでC-024が下したのと同じ判断。
- **UAT指摘の反映（C-048・2026-08-04）**: ①**商品ＩＤは非表示**（利用者にとって内部キーの表示が不要という判断）。列の`<th>`/`<td>`を`display:none`にする方式とし、要素は残してdatasetとの同期を維持している（要素を削除するとINSERT/UPDATEの振り分けと既存行判定が壊れる）。②**商品名称・備考の入力枠を各3文字分（全角basis 35px）拡張**（商品名称220→255px、備考190→225px、テーブル全体700→710px）。「シャープペンシル 0.5mm (10本入)」が見切れていたため。拡張幅はブラウザ上で実測した全角3文字＝34.3pxを根拠に35pxとした。
- **メニュー登録**: StartMenu・AdminMenuの両方に**非活性カードとして掲載済み**（C-042/C-043）。本画面の実装完了時に`name`属性へ`Sample/Html/Apps/ProductListMainte`を設定し`disabled`を外して有効化する。配置はStartMenu=マスタタブ列2、AdminMenu=マスタタブ列2。
- **受注明細との連携**: 受注明細は`商品ＩＤ`で本マスタを参照する（NOT NULL・FK。C-019のデータモデル是正）。ただし**受注明細側の入力を商品選択へ変える対応はC-044（第2段）**であり、本画面の実装時点では受注明細の商品名称は自由入力のまま。そのためC-044完了までは受注明細の**新規行追加ができない**（商品ＩＤがNOT NULLのため。2026-08-04実測で確認）。商品名称・受注単価は受注時点のスナップショットとして受注明細側に保持するため、本マスタの改名・論理削除は過去伝票に影響しない（データモデル設計書 業務ルール10・11）。

## 6. 画面遷移

| 遷移元 | 遷移先 | トリガ | 受け渡し項目 |
