## 0. 種別決定の経緯

本画面はHaluの標準5分類（Halu開発ガイド『画面タイプ』）のうち `list` の派生として実装されている（Halu開発ガイド『画面タイプ』「上記タイプに当てはまらない画面」節に明記）。検索条件エリアは持たず、バッチ管理テーブルの全件をバッチ管理ＩＤ降順でページング表示するのみのシンプルな一覧である。行クリックでバッチ管理ＩＤを選択し、「分割画面」「処理削除」の操作を行う。

対象テーブル（バッチ管理・バッチ分割管理・バッチパラメータ管理・バッチキー管理）はアプリ固有のデータモデルではなく、Haluフレームワークが内部的に自動管理するバッチ管理テーブル群である（Halu開発ガイド『バッチ処理』「5. batchtables」参照）。本画面はこれらのテーブルを参照・削除する管理者向け画面であり、通常の業務マスタ一覧とは性質が異なる。

## 1. 要件

| 要件ID | 区分 | 要件 | 背景・理由 |
|--------|------|------|-----------|
| REQ-012 | バッチ管理 | CSVアップロードの取込みはバッチ処理として実行し、実行状況を一覧・分割区分単位で確認・再処理できる | 大量データの取込みを画面応答をブロックせずに処理し、失敗時に部分再処理できるようにするため（10_要件定義/要件定義書.md 4.1） |
| REQ-012-1 | 表示 | バッチ管理一覧は20件ずつページングで表示する | 実装（dataset.json の defaultline="20"）から確認。他の一覧画面（UserList等）と同じページング方式に合わせたものと推定 |
| REQ-012-2 | 削除 | バッチ処理の削除は物理削除とし、子テーブル（バッチパラメータ管理・バッチキー管理・バッチ分割管理）→親テーブル（バッチ管理）の順に削除する | 参照整合性を保つため、子から親の順で削除する必要がある（データモデル設計書.md 4章 ルール8）。実装（BatchList_delete_sql.json のSQL連鎖順）から確認 |
| REQ-012-3 | 削除確認 | 処理削除の実行前に確認ダイアログを表示する | 誤操作による削除を防止するため。実装（controller.jsのexecuteDialog呼び出し）から確認 |

| 操作 | キー | 動作 | 遷移先 |

| 再表示 | F1 | 一覧を再照会して最新化する | - |

| 処理削除 | F3 | 選択行のバッチ管理レコードを、確認ダイアログ表示後、子テーブル→親テーブルの順に物理削除する | - |
| 最初 | F9 | 先頭ページへ移動 | - |
| 前 | F10 | 前ページへ移動 | - |
| 次 | F11 | 次ページへ移動 | - |
| 最後 | F12 | 最終ページへ移動 | - |
| 戻る | ESC | 遷移元のメニュー（StartMenu または AdminMenu）へ戻る | StartMenu / AdminMenu |

> **C-014（変更管理台帳）**: 旧仕様にあった「実行：F1」ボタンは、イベント未配線のデッドボタン（F1キーの実体は「再表示」）であったため2026-07-30付で廃止済み。現行ソース（index.html・appspec.js）が正であり、本設計書もそれに合わせて「実行」操作を含めていない。

## 5. 特記事項

- 処理削除（F3）は、一覧で行を選択してから操作する。未選択時は`check行選択()`によりガードされる（実装確認）。
- 分割画面（F2）にはコントローラ上の`check行選択()`ガードは無く、行選択状態の確認は画面遷移時のmixin共通処理（`checkNextStorageData()`によるsessionStorage遷移データの確認）に委ねられている（実装確認。2026-07-30 テスト仕様書精査時に記述を是正）。
- 「処理削除」は`freesql`を使わず、`genesql`のDELETE文4本（バッチパラメータ管理→バッチキー管理→バッチ分割管理→バッチ管理の順）を`sqls`配列で連鎖させる標準パターンで実装されている。CRUD宣言キーは不要（freesqlではないため）。
- 本画面が参照・削除する4テーブル（バッチ管理・バッチ分割管理・バッチパラメータ管理・バッチキー管理）はフレームワークの内部テーブルであり、業務データとしてのCRUD所有者はバッチサーバー（`halumain/batchserver.py`）である。本画面はその管理・削除のみを行うインターフェースである。
- 「分割画面」遷移で引き継ぐキーはバッチ管理ＩＤのみ（`nextStorageData`）。BatchDivisionList側は`beforeStorageData`でこれを受け取り、選択されたバッチの分割一覧を照会する。
- **戻る（ESC）の遷移先**: 実装の`on戻る`は`previousTransition`（遷移スタックの前画面へ戻る）であり、本画面は StartMenu・AdminMenu の両メニューに掲載されている（common.md 1.1。AdminMenuへの掲載はC-043）ため、戻り先は「遷移元のメニュー」となる。旧版で「StartMenuへ戻る」と記載していた疑義は 2026-09-21 の依頼者判断で「遷移元のメニュー（StartMenu または AdminMenu）」に確定し、4章・6章を同期した（承認記録簿 A-032）。

## 6. 画面遷移

| 遷移元 | 遷移先 | トリガ | 受け渡し項目 |
|--------|--------|--------|--------------|
| StartMenu / AdminMenu | 本画面 | メニュー（受注管理タブ）の「バッチ一覧」カードクリック（common.md 1.1。AdminMenuへの掲載はC-043） | - |
| BatchDivisionList | 本画面 | 「戻る」ボタン／ESCキー | - |
| 本画面 | BatchDivisionList | 行選択後「分割画面」ボタン／F2キー（common.md 1.2） | detail.バッチ管理ＩＤ（`nextStorageData`。`validation: required`） |
| 本画面 | StartMenu / AdminMenu | 「戻る」ボタン／ESCキー（`previousTransition`で遷移元のメニューへ戻る。4章・5章） | - |

「処理削除」（F3）は同一画面内でDELETEを実行するのみで画面遷移を持たない。本画面から起動する帳票・バッチはない（`OrderUpload`が起動したバッチの実行状況を照会する画面）。
