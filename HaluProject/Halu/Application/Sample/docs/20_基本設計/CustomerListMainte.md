## 0. 種別決定の経緯

顧客マスタ（顧客ＩＤ・顧客氏名・備考の3項目のみ）を対象に、一覧テーブル上で直接編集・追加・削除まで完結させる画面のため、`screen_types.md` の `list-mainte`（`SingleTableListForm*.mixin` 使用）に該当する。別画面への遷移は行わない。画面タイトルは「顧客一覧登録」で、list-mainteパターンの実装例としてSampleに配置されているもの（対象テーブルは顧客マスタ）。

---

## 1. 要件

| 要件ID | 区分 | 要件 | 背景・理由 |
|--------|------|------|-----------|
| REQ-001 | 表示 | 削除フラグ='0'の顧客を全件、一覧テーブルに表示する（ページングなし） | 一覧＋行編集で完結させる方針のため全件表示とする |
| REQ-002 | 編集 | 一覧内で顧客氏名・備考をテーブルセル上で直接編集できる | 別画面遷移せず一覧内で完結させるため（list-mainteパターン） |
| REQ-003 | 追加 | 「行追加」ボタンで末尾に空行を追加し、新規顧客を登録できる | 顧客ＩＤはSERIAL自動採番のため、新規行では入力不要 |
| REQ-004 | 削除 | 「削除」列のチェックボックスにチェックを付けた行のみを、「削除」ボタン押下で削除できる。チェック無しで押下した場合は警告する | 誤操作防止（C-012 UAT指摘） |
| REQ-005 | 選択操作性 | 「全選択」ボタンで、既存行（顧客ＩＤ入力済み）の削除チェックを一括ON/OFF（トグル）できる | 複数件削除時の操作性向上（C-011） |
| REQ-006 | 登録 | 「登録」ボタン押下時、削除チェックの無い行のみを対象に、顧客ＩＤの有無でINSERT/UPDATEを自動判定する | 一覧上の新規追加行と既存行の混在編集に対応するため |

## 4. 操作

| 操作 | キー | 動作 | 遷移先 |
|------|------|------|--------|
| 全選択 | - | 顧客ＩＤが入力済みの行（＝既存行）の削除チェックを一括ON/OFF（トグル）する。新規追加行（顧客ＩＤ空欄）は対象外 | - |
| 行追加 | - | 明細末尾に空行を1行追加し、追加した行の顧客氏名欄へフォーカスする | - |
| 削除 | - | 削除チェックのある行のみを対象に削除を実行する。チェック0件の場合は警告メッセージを表示し送信しない | - |
| 登録 | F1 | 削除チェックの無い行のみを対象に、顧客ＩＤの有無でUPDATE／INSERTを振り分けて一括登録する | - |
| 戻る | ESC | メニュー画面へ戻る | StartMenu / AdminMenu |

## 5. 特記事項

- **execKindによるクライアント側の行フィルタ**: 「登録」「削除」ボタンはいずれも同じ`execute`トランザクションを実行するが、コントローラが`this.model.execKind`に`"register"`／`"delete"`をセットし、`on実行OfCheckRequestData`（`CustomerListMainte.model.js`）が送信直前に削除チェック値で明細行を絞り込む（登録＝チェック無し行のみ、削除＝チェック有り行のみ）。**実装上の注意（C-026）**: `SingleTableListFormModelMixin`の`on照会OfCheckRequestData`は`on実行OfCheckRequestData`へ委譲するため、この行フィルタは必ず`mode == "execute"`のガード付きで実装する（ガード無しだとselect（照会）時にも絞り込みが走り、selectリクエストの空のdetailレコードに対して例外となり初期照会が沈黙する）。
- **UPDATE/INSERTの自動判定**: サーバー側`CustomerListMainte_execute_sql.json`は`update`→`insert`→再照会（`detail`）の順で定義されており、共通クラス`SingleTableListForm_model.setData`（`Sample/Server/Commons/SingleTableListFormModel.py`）が、送信された明細行のうち顧客ＩＤが入っている行を`update`用SQLの入力に、顧客ＩＤが空欄の行を`insert`用SQLの入力に振り分ける。**顧客ＩＤの採番はDBのSERIALに委ねる（C-026で是正）**: `insert`用SQLの`input.record`には顧客ＩＤを**含めない**（`setInsertData`内部の「送信行の最大＋1」採番は送信データ上の空欄埋めであり、DBへは送らない。これをSQL入力に含めると、論理削除済み行のＩＤと衝突して主キー重複になる）。また`insert`の`削除`（削除フラグ）は画面値ではなく**`funct: "'0'"`でリテラル固定**とする（新規行の画面値は空のため、画面値のまま登録すると`削除フラグ='0'`の照会条件から漏れて登録直後の行が一覧に表示されない）。削除（`delete`と紐づくSQLは本画面にはなく、削除は`update`/`insert`と同じ`execute`トランザクション内で、クライアント側フィルタにより「削除チェック有り行のみ」を送信することで実現している点に注意（サーバー側は"通常の更新"として処理し、削除フラグを'9'のまま保存する。物理削除ではなく削除チェック値の保存にとどまる）。
- 「全選択」はモデル側`on全選択`が、顧客ＩＤが入っている行のみを対象に全ON/全OFFを判定・トグルする（新規行は対象外）。

### 実装上の不具合・疑義（報告のみ・修正不可）

- `CustomerListMainte_execute_tran.json`のレスポンス（`detail`レコード）に`購入回数`という項目が定義されているが、`dataset.json`・`execute_sql.json`・`select_sql.json`・`index.html`のいずれにも存在しない孤立フィールドである。動作への影響はない（tran.json内で完結し、どこからも参照されない）が、コピー&ペーストの残骸である可能性が高い。
- 削除チェック済みの行を「登録」実行した場合、`on実行OfCheckRequestData`のkeep条件により当該行はサーバーへ送信されない。新規追加行（顧客ＩＤ未採番）に削除チェックを付けて登録すると、画面上から行が消えるだけでDBには何も登録されない（＝実質的な取り消し）。既存行に削除チェックを付けたまま登録した場合も同様にサーバーへ送信されず、削除も更新もされない。この挙動が意図された仕様か、UI上の考慮漏れかは実装から判断できないため、業務上問題がないか要確認。
